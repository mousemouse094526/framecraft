# Decisions: spoil-maker

## D1: เป็น feature ใหม่ชื่อ spoil-maker ใน tab สปอย

**Chosen:** การสร้างคลิปสปอย (บท, เสียงบรรยาย, จับคู่ภาพ, render) เป็น feature ใหม่ `spoil-maker` ที่อยู่ใน tab สปอยและใช้ Temp clip กับ Transcript ของ spoil.

**Why:** มีข้อมูลของตัวเอง (บท, เสียง, ผล render) และใช้งานแยกได้; spec ของ spoil จะใหญ่เกินไปถ้าต่อในนั้น. ผู้ใช้เลือกชื่อเอง.

**Rejected:**
- เป็น change request ของ spoil — spec ของ spoil ใหญ่ขึ้นมากจนอ่านยาก
- ชื่อ `spoil-cut`, `auto-edit`, `spoil-short`, `narrated-cut` — ผู้ใช้เลือก `spoil-maker`

**From:** interview · **Status:** changed by D53

## D2: ทุกอย่างต้องฟรี

**Chosen:** ทุกส่วนของ spoil-maker ใช้ของฟรีเท่านั้น: โมเดลและโปรแกรมที่รันในเครื่อง ไม่มี API ที่ต้องจ่ายเงินหรือต้องผูกบัตร.

**Why:** ผู้ใช้กำหนด.

**Rejected:**
- API ของ LLM บน cloud ที่เก็บเงินตามการใช้ — ไม่ฟรี

**Details:**
- เครื่องที่ใช้ทำ feature นี้คือ Mac Apple M2 RAM 16 GB และมี Ollama ติดตั้งผ่าน Homebrew อยู่แล้ว — ข้อมูลสำหรับเลือกโมเดล ยังไม่ใช่การตัดสินว่าใช้ Ollama

**From:** interview · **Status:** active

## D3: ยังไม่คิดเรื่อง license ตอนนี้ ใช้ OmniVoice ไปก่อน

**Chosen:** รอบนี้ใช้โมเดลที่มีอยู่ได้ รวม OmniVoice ที่เป็น CC BY-NC. ทำให้ใช้งานได้ก่อน แล้วค่อยเปลี่ยนเป็นโมเดลหรือวิธีอื่นเมื่อจะใช้หารายได้.

**Why:** ผู้ใช้อยากได้ของที่ใช้ได้ก่อน แล้วค่อยหาตัวแทน.

**Rejected:**
- เลือกเฉพาะโมเดลที่ใช้เชิงพาณิชย์ได้ตั้งแต่ต้น — ผู้ใช้ไม่ต้องการให้เรื่องนี้ขวางรอบแรก

**Details:**
- ทำตาม ADR-0007 ต่อ: ผลงานที่ใช้ OmniVoice ใช้ส่วนตัวหรือทดลองเท่านั้น และต้องใส่เครดิตโมเดล
- ส่วนที่ใช้ TTS ต้องเปลี่ยนโมเดลได้โดยไม่รื้อส่วนอื่น เพื่อให้เปลี่ยนตัวแทนได้ภายหลัง

**From:** interview · **Status:** changed by D41

## D4: AI ร่างบทสปอย แล้วผู้ใช้แก้ก่อนสร้างเสียง

**Chosen:** LLM ในเครื่องร่างบทสปอยจาก Transcript ของต้นฉบับ ผู้ใช้แก้บทได้ทุกประโยคก่อนสร้างเสียงบรรยาย.

**Why:** โมเดลเล็กที่รันฟรีในเครื่อง (D2) เขียนภาษาไทยได้ไม่เนียนเท่าโมเดลบน cloud จึงต้องให้ผู้ใช้แก้ได้.

**Rejected:**
- AI ทำเองทั้งหมดโดยไม่มีขั้นแก้บท — บทจากโมเดลเล็กอาจผิดหรือไม่เป็นธรรมชาติ
- ผู้ใช้วางบทเองอย่างเดียว — ผู้ใช้อยากให้ AI ร่างให้
- ได้ทั้ง AI ร่างและวางบทเอง — ผู้ใช้เลือกแบบ AI ร่างแล้วแก้

**From:** interview · **Status:** active

## D5: คลิปสปอยหนึ่งคลิปทำจาก Temp clip ได้หลาย EP

**Chosen:** ผู้ใช้เลือก Temp clip ที่ถอดแล้วตั้งแต่ 1 คลิปขึ้นไป เรียงลำดับเองได้ แล้วได้คลิปสปอยหนึ่งคลิปที่เล่าเรื่องรวมทุก EP ที่เลือก.

**Why:** ผู้ใช้เลือกตามคลิปตัวอย่าง BLACKCASEFILE ที่สรุปทั้งคดีที่อาจยาวหลาย EP.

**Rejected:**
- 1 EP ต่อ 1 คลิปสปอยเท่านั้น — สรุปเรื่องที่ยาวหลาย EP ไม่ได้
- 1 EP แบ่งเป็นหลายคลิปสปอย — ผู้ใช้ไม่เลือกในรอบนี้
- ทุกแบบ — งานเยอะเกินรอบแรก

**Details:**
- ทุกคลิปที่เลือกต้องถอดแล้ว (มี Transcript) เพราะ AI ร่างบทจาก Transcript (D4)

**From:** interview · **Status:** active

## D6: เสียงบรรยายจาก OmniVoice เลือกเสียงได้และ clone จากไฟล์เสียงสั้นได้

**Chosen:** OmniVoice สร้างเสียงบรรยายจากบทที่ผู้ใช้แก้แล้ว (D4). ผู้ใช้เลือกเสียงจากรายการเสียงตัวอย่าง หรือใส่ไฟล์เสียงสั้นๆ ของตัวเองให้ clone ได้ และใช้เสียงเดิมซ้ำได้ทุกคลิป.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: เสียงคงที่ทุกคลิปเหมือนช่องสปอยจริง และ OmniVoice ติดตั้งไว้แล้ว (D3).

**Rejected:**
- OmniVoice เสียงเดียว ไม่มีให้เลือก — ผู้ใช้อยากเลือกเสียง
- ผู้ใช้อัดเสียงเองแล้ว AI จับเวลา — ผู้ใช้ไม่เลือก
- ได้ทั้ง OmniVoice และอัดเอง — งานเยอะกว่า

**Details:**
- ลองแล้วใน [tts-trial.md](tts-trial.md): อ่านไทยได้ดี, clone ไฟล์ 3–10 วินาทีได้แต่บางไฟล์เสีย
- เสียงตัวอย่างคือ Saved voice ที่ผู้ใช้ออกแบบเอง (D32)

**From:** interview · **Status:** changed by D48

## D7: เลือก preset สไตล์ 3 แบบ แล้วใส่ความยาวเป้าหมายเอง

**Chosen:** ผู้ใช้เลือกสไตล์จาก 3 preset ตามคลิปตัวอย่าง แล้วใส่ความยาวเป้าหมายของคลิปสปอยเป็นวินาที. AI ร่างบทให้ยาวพอดีกับความยาวนั้น.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: ได้สไตล์ที่รู้ว่าใช้ได้จากช่องจริง และยังคุมความยาวได้.

**Rejected:**
- preset ที่ความยาวตายตัว — คุมความยาวไม่ได้
- สไตล์เดียวในรอบแรก — ผู้ใช้อยากได้ทั้ง 3 แบบ
- ผู้ใช้เขียน prompt เอง — ผู้ใช้ไม่เลือก

**Details:**
- preset มาจาก [reference-shorts.md](reference-shorts.md): ปั่นตัดเร็ว (Popcorn Pop), เล่าละครหักมุม (BLACKCASEFILE), เล่าตามลำดับ (eed_closet)
- ความเร็วพูดของตัวอย่างราว 9–11 ตัวอักษรต่อวินาที; ใช้ความเร็วพูดที่วัดจาก Saved voice ประมาณความยาวบทแทน (D35)
- ช่วงความยาวที่ใส่ได้ (ต่ำสุดและสูงสุด) ยังไม่ได้ตัดสิน

**From:** interview · **Status:** active

## D8: Layout 3 แบบ เลือกแยกจากสไตล์

**Chosen:** มี layout 3 แบบตามคลิปตัวอย่าง ผู้ใช้เลือกคู่กับสไตล์ไหนก็ได้ และแต่ละสไตล์ (D7) มี layout ตั้งต้น.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: ใช้ภาพแบบหนึ่งกับวิธีเล่าอีกแบบได้.

**Rejected:**
- layout ผูกกับสไตล์ — เลือกผสมไม่ได้
- layout เดียวในรอบแรก — ผู้ใช้อยากได้ทั้ง 3 แบบ

**Details:**
- layout ตาม [reference-shorts.md](reference-shorts.md): เต็มจอ 9:16 มี hook ค้างด้านบนกับซับทีละคำ; ภาพ 16:9 บนพื้นดำกับซับเป็นประโยค; ชื่อตอนค้างด้านบนกับภาพ 16:9
- ทุก layout ได้วิดีโอ 1080×1920
- รายละเอียดของแต่ละ layout (ตำแหน่ง, font, สี, ข้อความที่ผู้ใช้ใส่เอง) ยังเป็น sketch ใน map

## D9: เสียงต้นฉบับลดเบาไว้ใต้เสียงบรรยาย ตั้งระดับได้

**Chosen:** เสียงของช่วงภาพต้นฉบับที่ใช้ยังอยู่ แต่เบากว่าเสียงบรรยาย. ผู้ใช้ตั้งระดับเสียงต้นฉบับได้ และ 0 คือปิด. ไม่มีเพลงพื้นหลังในรอบนี้.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: ได้บรรยากาศเดิมโดยไม่กลบเสียงบรรยาย.

**Rejected:**
- ปิดเสียงต้นฉบับเสมอ — เสียบรรยากาศ
- ลดเบาและใส่เพลงพื้นหลังของผู้ใช้ — ผู้ใช้ไม่เลือกในรอบนี้

**Details:**
- ค่าตั้งต้นของระดับเสียงต้นฉบับยังไม่ได้ตัดสิน

**From:** interview · **Status:** active

## D10: ผลลัพธ์เป็น mp4 กับ .srt ของบทบรรยาย

**Chosen:** render ได้ mp4 1080×1920 ที่พร้อมลง และไฟล์ `.srt` ของบทบรรยาย. แก้ต่อในแอปแล้ว render ใหม่ ไม่มีไฟล์ project ของโปรแกรมตัดต่ออื่น.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: `.srt` ใช้ใส่ซับแยกบน YouTube หรือ TikTok ได้.

**Rejected:**
- mp4 อย่างเดียว — ไม่มีซับแยก
- ไฟล์ project ไปแก้ต่อในโปรแกรมตัดต่อ (เช่น FCPXML) — งานเยอะขึ้นมาก

**From:** interview · **Status:** active

## D11: บทบรรยายเป็นภาษาไทยอย่างเดียว

**Chosen:** บทสปอยและเสียงบรรยายเป็นภาษาไทยเสมอ ไม่ว่าต้นฉบับเป็นภาษาอะไร.

**Rejected:**

**From:** interview · **Status:** active

## D12: LLM รันด้วย library ใน .venv ตาม ADR ไม่ใช้ Ollama

**Chosen:** LLM ที่เขียนบทและจับคู่ภาพรันด้วย library Python ใน `.venv` ของ project. โมเดลโหลดจาก Hugging Face ที่ pin commit ลง `models/` ผ่าน Setup script, ลงทะเบียนใน `backend.models` และมีแถวใน Status check. library ตัวไหน (เช่น llama-cpp-python, mlx-vlm, transformers) ตัดสินหลังลองโมเดลจริง.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: ทำตาม ADR-0003, ADR-0004, ADR-0008 และ ADR-0009 ต่อ ก๊อป folder ไปเครื่องอื่นแล้วรัน Setup script ซ้ำได้เหมือนเดิม.

**Rejected:**
- ใช้ Ollama ที่ติดตั้งด้วย Homebrew — อยู่นอก project และโมเดลไม่ได้ pin ใน `backend.models` ต้อง supersede ADR-0003, ADR-0004, ADR-0008
- รองรับทั้ง `.venv` และ Ollama ผ่าน adapter — งานมากขึ้นโดยไม่จำเป็นรอบแรก

**Details:**
- library ต้องรันได้บน Mac (Metal/MPS) และมีทางไป Windows NVIDIA (ADR-0006); เช็ค Windows เป็นงานของ `windows-check` (ADR-0014)
- งานที่ใช้ LLM รันใน process ลูกตาม ADR-0012

**From:** interview · **Status:** active

## D13: Qwen3.5 9B เขียนบทและจับคู่ภาพ

**Chosen:** LLM ของ spoil-maker คือ Qwen3.5 9B แบบ 4-bit (`mlx-community/Qwen3.5-9B-MLX-4bit` revision `938d8919941c6e7efd3c7150eff7fe9d12afa631`, Apache-2.0, 6.0 GB) ลงทะเบียนใน `backend.models` ตาม D12.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: จากการลองใน [llm-trial.md](llm-trial.md) บทยาวใกล้เป้าหมาย เล่าตามเรื่องจริงได้ ดูภาพได้แม่นกว่าตัวอื่น และ license ใช้หารายได้ได้.

**Rejected:**
- Gemma 4 E4B — เร็วกว่า 2 เท่าแต่บทสั้นและไม่เล่าเรื่องหนัง
- Typhoon 2.5 Qwen3 4B — เขียน JSON ไม่จบเมื่อ Transcript ยาว
- ลอง prompt หรือโมเดลอื่นเพิ่มก่อน — ผู้ใช้ไม่เลือก

**Details:**
- ร่างบทจาก Transcript หนัง 96 นาที (ราว 26,000 token) ในครั้งเดียวใช้ราว 263 วินาที และ memory สูงสุด 9.9 GB บน M2 16 GB
- ใช้ memory มากจนรันพร้อมงาน GPU อื่น (Whisper, OmniVoice) ไม่ได้: ต้องรันทีละงาน
- จับคู่ประโยคกับบรรทัดของ Transcript ได้ตรงราวครึ่งหนึ่ง ภาษาไทยยังต้องแก้ (D4)

**From:** research · **Status:** active

## D14: รัน LLM ด้วย mlx-vlm บน Mac ส่วน Windows ตัดสินใน windows-check

**Chosen:** บน Mac รัน Qwen3.5 9B ด้วย mlx-vlm ใน `.venv` (D12). ส่วนเรียก LLM อยู่หลัง interface ที่เปลี่ยน backend ได้. backend สำหรับ Windows NVIDIA (เช่น transformers หรือ llama.cpp) เลือกและลองใน `windows-check` ตาม ADR-0014; จนกว่าจะทำ แถว Status check ของ LLM บน Windows ไม่ผ่าน.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: mlx-vlm ลองแล้วว่าใช้ได้บน Mac และ ADR-0014 ให้ feature จบได้เมื่อผ่านบน Mac.

**Rejected:**
- llama-cpp-python ทั้งสอง OS — ยังไม่ได้ลองว่ารองรับ Qwen3.5 และภาพ, wheel CUDA บน Windows ติดตั้งยากกว่า
- ลอง llama-cpp-python ก่อนตัดสิน — ผู้ใช้ไม่เลือก

**Details:**
- mlx-vlm รันได้เฉพาะ Apple Silicon; ลองกับ mlx-vlm 0.7.11
- mlx-vlm ต้องติดตั้งเฉพาะ `sys_platform == 'darwin'` ใน `pyproject.toml`

**From:** interview · **Status:** changed by D50

## D15: AI จับคู่ภาพจาก Transcript และคำบรรยายภาพของทุก shot

**Chosen:** ต้นฉบับแต่ละคลิปถูกตัดเป็น shot และ LLM (D13) บรรยายเฟรมของทุก shot เก็บไว้คู่ Temp clip ทำครั้งเดียวต่อคลิป. ตอนร่างบท LLM เลือก shot ให้แต่ละประโยคจากทั้ง Transcript และคำบรรยายภาพ.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: จาก [llm-trial.md](llm-trial.md) จับคู่จาก Transcript อย่างเดียวตรงราวครึ่งหนึ่ง และใช้ฉากที่ไม่มีบทพูดไม่ได้เลย.

**Rejected:**
- Transcript อย่างเดียว — จับคู่ผิดราวครึ่งหนึ่ง และฉากไม่มีบทพูดใช้ไม่ได้
- ดูภาพเฉพาะรอบช่วงที่เลือกจาก Transcript — ฉากไม่มีบทพูดยังหลุด

**Details:**
- บรรยายภาพละราว 4–7 วินาทีบน M2 (ลอง 3 เฟรม); หนัง 1.5 ชั่วโมงอาจมีหลายร้อยถึงหลายพัน shot จึงใช้เวลานาน
- วิธีตัด shot, เฟรมไหนของ shot, และเริ่มงานเมื่อไร ยังเป็นคำถามใน map

## D16: บรรยายภาพเมื่อผู้ใช้กดปุ่มของแต่ละคลิป

## D18: ร่างบทสองขั้น: บทจาก Transcript ก่อน แล้วเลือก Shot ทีละประโยค

**Chosen:** ขั้นแรก LLM (D13) ร่างบทจาก Transcript อย่างเดียว แต่ละประโยคอ้าง 1–3 บรรทัดของ Transcript. ผลที่ JSON พังหรือจำนวนประโยคห่างจากเป้าหมายเกินกำหนด สั่งใหม่ได้สูงสุด 3 ครั้ง. ขั้นที่สอง ต่อประโยค ส่งเฉพาะ Shot ที่อยู่ในช่วง ±30 วินาทีรอบบรรทัดที่อ้าง พร้อม Shot description ให้ LLM เลือก 2 Shot.

**Details:**

- ตัดอักษรจีนที่หลุดมาในบทไทยออก (เจอ `扫墓`, `来抓`, `現場`)
- หนัง 96 นาที: ขั้นแรกราว 263 วินาที (รอบ 1) + ขั้นสองราว 5 วินาทีต่อประโยค, memory ราว 10 GB

## D30: สร้างเสียงได้ทั้งหมดหรือทีละประโยค และ render สร้างส่วนที่ขาดให้

**Chosen:** หน้าตรวจแก้มีปุ่ม "สร้างเสียงทั้งหมด" ที่สร้างเฉพาะประโยคที่ยังไม่มีเสียงหรือต้องสร้างใหม่. แต่ละประโยคฟังเสียงและสร้างใหม่ได้. แก้ข้อความของประโยคที่มีเสียงแล้ว เสียงนั้นเป็น "ต้องสร้างใหม่". กด render ตอนยังมีประโยคที่ขาดเสียง render สร้างให้ก่อน. สถานะของประโยคตาม [review-sketch.md](review-sketch.md) › สถานะของแต่ละประโยค.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: ฟังและแก้ทีละประโยคได้โดยไม่ต้อง render ทั้งคลิป และเห็นความยาวจริงก่อน render.

**Rejected:**
- สร้างเสียงตอน render เท่านั้น — ฟังได้แค่ในคลิปที่ render แล้ว แก้ประโยคเดียวต้อง render ทั้งคลิป
- สร้างอัตโนมัติหลังร่างบท — ขัด D4 และเสียเวลาสร้างเสียงที่จะถูกแก้

**Details:**
- ความยาวรวมบนหน้าตรวจแก้: ประโยคที่มีเสียงใช้ความยาวจริง, ที่ยังไม่มีใช้ค่าประมาณจากจำนวนตัวอักษรกับความเร็วพูดของ Saved voice (D35)
- OmniVoice ใช้ราว 8–20 วินาทีต่อประโยคบน M2 ([tts-trial.md](tts-trial.md) › เวลาและ memory)

## D32: เสียงตัวอย่างคือเสียงที่ผู้ใช้ออกแบบเองแล้วบันทึกไว้

**Chosen:** ผู้ใช้เลือกเพศ วัย และระดับเสียง กดสุ่ม ฟังประโยคตัวอย่าง แล้วตั้งชื่อบันทึกเสียงที่ชอบเป็น Saved voice. OmniVoice สร้างประโยคตัวอย่างด้วย voice design แล้วเก็บผลเป็น clone prompt ใช้กับทุกประโยค ทุกคลิป. เสียงที่ clone จากไฟล์ของผู้ใช้ (D6) ก็เป็น Saved voice อยู่ในรายการเดียวกัน.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: OmniVoice ไม่มีเสียงสำเร็จรูป และ voice design สุ่มเสียงใหม่ทุกครั้ง ([tts-trial.md](tts-trial.md)); ให้ผู้ใช้ฟังแล้วเลือกเองได้เสียงที่ชอบจริงและเป็นเสียงเดิมทุกครั้ง.

**Rejected:**
- ชุดเสียงตายตัว 4 เสียงที่ project สร้างด้วย seed ตายตัว — ปรับไม่ได้ และ seed เดียวกันอาจได้เสียงต่างกันข้ามเครื่อง
- ทั้งชุดตายตัวและออกแบบเอง — งานมากสุด
- ไม่มีเสียงตัวอย่าง clone อย่างเดียว — ขัด D6

**Details:**
- คุณสมบัติที่เลือกได้ตาม `instruct` ของ OmniVoice: เพศ (ชาย, หญิง), วัย (เด็ก ถึง สูงอายุ), ระดับเสียง (ต่ำมาก ถึง สูงมาก). ไม่มีสำเนียงและเสียงกระซิบ
- ลองแล้ว: เสียงล็อกจาก voice design อ่านไทย CER 4–7% ([tts-trial.md](tts-trial.md) › ผล)
- ยังไม่ได้ฟังด้วยหูว่าเสียงล็อกเป็นเสียงเดียวกันทุกประโยค: map › `num_step` 16 หรือ 32 ให้ผู้ใช้ฟังพร้อมกัน

**From:** research · **Status:** changed by D48

## D33: clone ฟังประโยคตัวอย่างก่อนบันทึก ไม่มีตรวจอัตโนมัติ

**Chosen:** ผู้ใช้ใส่ไฟล์เสียงแล้ว OmniVoice สร้างประโยคตัวอย่างให้ฟังเหมือนการออกแบบเสียง (D32). ผู้ใช้เลือกบันทึกเป็น Saved voice หรือทิ้ง. ไม่มีการตรวจอัตโนมัติว่า clone ใช้ได้.

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: บางไฟล์ clone แล้วอ่านผิดทั้งประโยคและดูจากไฟล์ไม่รู้ ([tts-trial.md](tts-trial.md) › ผล) แต่ผลที่เสียฟังออกทันที; flow เดียวกับ D32.

**Rejected:**
- ฟังแล้วตรวจด้วย Whisper เตือนเมื่อผิดเกิน 20% — ต้องสลับโหลด Whisper กับ OmniVoice ช้าลง 10–20 วินาที
- ตรวจทุกประโยคที่สร้างด้วย Whisper — งานและเวลาเพิ่มทุกคลิป

**Details:**
- เสียงที่บันทึกแล้วยังอ่านผิดบางประโยคได้ ผู้ใช้สร้างใหม่ทีละประโยค (D30)

## D34: ไฟล์ clone ใช้ 3–10 วินาทีแรก Whisper ถอดข้อความให้ผู้ใช้แก้ได้

**Chosen:** ไฟล์เสียงที่ใช้ clone สั้นกว่า 3 วินาทีไม่รับ. ยาวกว่า 10 วินาทีใช้ 10 วินาทีแรก. Whisper ถอดข้อความของช่วงที่ใช้ แล้วผู้ใช้แก้ข้อความได้ก่อนสร้างประโยคตัวอย่าง (D33).

**Rejected:**
- ตัด 10 วินาที ผู้ใช้พิมพ์ข้อความเอง — ผู้ใช้ต้องพิมพ์ทุกคำ
- ผู้ใช้เลือกช่วง 3–10 วินาทีบนคลื่นเสียง — ได้ช่วงที่สะอาดที่สุดแต่ UI มากขึ้น

**Details:**
- Whisper ถอดไฟล์ที่ตัดแล้ว ข้อความจึงตรงกับเสียงแม้ตัดกลางคำ
- Whisper กับ OmniVoice เป็นงาน GPU ทีละงาน (ADR-0012)

**From:** interview · **Status:** superseded by D48

## D35: Saved voice มี speed ของตัวเอง และความเร็วพูดที่วัดได้ใช้ประมาณความยาวบท

**Chosen:** ตอนออกแบบเสียง (D32) หรือ clone (D33) ผู้ใช้ปรับ speed 0.8–1.2 (ค่าเริ่มต้น 1.0) แล้วฟังประโยคตัวอย่าง. speed บันทึกคู่ Saved voice และใช้กับทุกประโยคที่สร้างด้วยเสียงนั้น. ความเร็วพูด (ตัวอักษรต่อวินาที) วัดจากประโยคตัวอย่างตอนบันทึก แล้วใช้แทนค่า 9–11 ตัวอักษรต่อวินาทีของ D7 ในการให้ LLM ร่างบทยาวพอดีความยาวเป้าหมาย และในความยาวประมาณบนหน้าตรวจแก้ (D30).

**Why:** ผู้ใช้เลือกตัวเลือกที่แนะนำ: OmniVoice พูด 12–16 ตัวอักษรต่อวินาทีและต่างกันตามเสียง ค่าเดียวประมาณผิด; speed 0.8–1.2 ไม่ทำให้อ่านผิดเพิ่ม ([tts-trial.md](tts-trial.md) › รอบ 2: `speed` และตัวเลข).

**Rejected:**
- ไม่ปรับ speed ใช้ค่าที่วัดได้อย่างเดียว — พูดเร็วกว่าคลิปตัวอย่างเสมอ
- speed ตาม preset สไตล์ — ไม่สนใจว่าแต่ละเสียงเร็วต่างกัน

**Details:**
- นับตัวอักษรไม่รวมช่องว่างและวรรคตอน แบบเดียวกับที่วัดใน [tts-trial.md](tts-trial.md)
- เปลี่ยน speed ของ Saved voice ที่บันทึกแล้วไม่ได้: ออกแบบหรือ clone ใหม่ — ตัดสินตอนเขียน spec

## D36: แปลงตัวเลขเป็นคำไทยเฉพาะข้อความที่ส่งให้ OmniVoice

**Chosen:** ก่อนสร้างเสียง backend แปลงตัวเลขในประโยคเป็นคำอ่านไทย (`1968` → `หนึ่งพันเก้าร้อยหกสิบแปด`, `114,000` → `หนึ่งแสนหนึ่งหมื่นสี่พัน`) แล้วส่งข้อความที่แปลงให้ OmniVoice. บทบนหน้าตรวจแก้, ซับบนคลิป และ `.srt` ยังเป็นตัวเลขตามที่เขียน.

**Rejected:**
- สั่ง LLM เขียนตัวเลขเป็นคำ — ซับยาวอ่านยาก และตัวเลขที่ผู้ใช้พิมพ์เองยังอ่านผิด
- เตือนประโยคที่มีตัวเลขบนหน้าตรวจแก้ — ผู้ใช้ต้องแก้เอง และแก้แล้วซับกลายเป็นคำ

**Details:**
- ความเร็วพูดที่ใช้ประมาณความยาว (D35) นับจากข้อความที่แปลงแล้ว
- แปลงด้วย library (`num2words` มีภาษาไทย ต้องติดตั้งผ่าน Setup script และมีแถวใน Status check ตาม ADR-0002, ADR-0009) หรือเขียนเอง — ตัดสินตอนเขียน spec
- ทศนิยม, เวลา (`10:30`), เลขไทย (`๑๙๖๘`) — ตัดสินตอนเขียน spec

**Why:** เช็คมือบน M2 (Seam 3) ด้วยหนัง 96 นาที 840 Shot: เฟรม 640 ใช้ราว 64 นาที (4.5 วินาที/Shot, prompt 248 token) เกินเป้า 60 นาที; เฟรม 448 ใช้ 52.7 นาที (3.2 วินาที/Shot, prompt 140 token) และสุ่ม 10 Shot ตรงภาพ 9 ทั้งสองขนาด. ผู้ใช้เลือก.

**Rejected:**
- คง 640 แล้วขยายเป้าเป็น 65 นาที — ช้ากว่าที่ spec สัญญา
- ลด `max_tokens` — คำบรรยายยาวราว 30 token อยู่แล้ว ไม่เร็วขึ้น

## D58: ปุ่ม "ดูภาพ" เปลี่ยนเป็น "บรรยายฉาก" พร้อมบรรทัดอธิบาย

**Chosen:** คำบนจอของ Describe job เปลี่ยนจาก "ดูภาพ" เป็น "บรรยายฉาก" ทุกที่ (ปุ่ม, ป้าย "บรรยายฉากแล้ว", คำยืนยันทำใหม่, ข้อความ error และ `gpu_busy`); ขั้น `cutting` บอก "กำลังแบ่งฉาก" แทน "กำลังหาจุดตัดภาพ"; ใต้ปุ่มมีบรรทัด "ให้ AI เขียนว่าแต่ละฉากมีภาพอะไร ใช้ตอนร่างบทสปอย" ซึ่งเป็น accessible description ของปุ่ม และถูกแทนด้วยเหตุผลเมื่อมีงาน GPU อื่น. ชื่อในโค้ดและ API (`describe`, Shot) ไม่เปลี่ยน.

**Why:** ผู้ใช้ลองแล้วไม่เข้าใจว่า "ดูภาพ" ทำอะไร: ฟังเหมือนเปิดดูรูปเอง ไม่บอกว่า AI เขียนคำบรรยาย และไม่บอกว่าผลไว้ใช้ตอนร่างบท. ผู้ใช้เลือก.

**Rejected:**
- "อ่านภาพในคลิป" — คู่กับ "ถอดบทพูด" แต่ยังไม่บอกว่าได้คำบรรยาย
- คง "ดูภาพ" แล้วเพิ่มแค่บรรทัดอธิบาย — คำบนปุ่มยังกำกวม

**From:** ผู้ใช้หลัง build ticket 01 · **Status:** active

## D61: เลือก Shot ส่งให้ AI ไม่เกิน 40 Shot; บทเก็บ ref ประโยคละ 3; temperature ร่างบท 0.3

**Chosen:** ข้อ 5.3 ของ Draft job ส่ง Shot ในช่วงให้ Qwen ไม่เกิน 40 Shot ที่ใกล้เวลาเริ่มของ ref แรกที่สุด (เรียงตามเลข); คำตอบที่ไม่อยู่ใน Shot ที่ส่งไปใช้ 2 Shot ที่ใกล้ที่สุดในนั้น. ช่วง (`window`) และตัวเลือก Shot ไม่เปลี่ยน. temperature ของร่างบทเป็น 0.3 (เดิม 0.7, spec › ค่าการสร้างข้อความ). คำสั่งร่างบทบอกกฎ (สไตล์ ความยาว จำนวนประโยค ตัวอักษรต่อประโยคไม่เกิน `1.2 × target_letters / จำนวนประโยค`, ref 1–3 ไม่อ้างเป็นช่วง, JSON) ทั้งก่อนและหลัง Transcript; ครั้งที่ 2–3 บอกเพิ่มว่าครั้งก่อนยาวหรือสั้นไปเท่าไร หรือไม่ได้ JSON ครบ; ประโยคเก็บ ref แค่ 3 ตัวแรกที่มีจริง; JSON ที่ขาดแค่ `}` ตัวสุดท้ายอ่านได้.

**Why:** รันจริงบนหนัง 96 นาที (840 Shot): ประโยคที่อ้างบรรทัดห่างกันมากได้ช่วงเกือบทั้งเรื่อง ส่งหลายร้อย Shot ในคำสั่งเดียว เลือกเกิน 60 วินาที งานทั้งงาน `failed`. วัดบน M2: Qwen อ่านราว 0.4 วินาทีต่อ Shot (15 Shot 8 วินาที, 40 Shot 17 วินาที, 80 Shot 33 วินาที). ช่วงปกติ ±30 วินาทีมี 9–17 Shot จึงไม่ถูกตัด. จำกัดความยาววิดีโอไม่ช่วย: ref ห่างกัน 20 นาทีก็ยังเกิน. ร่างบทจริง 2 ครั้งแรกจาก 3 ได้ JSON ที่ถูกตัด: Qwen ใส่ `refs` ประโยคละ 20–60 id จนครบ `max_tokens` (Transcript ทั้งเรื่องราว 30k token อยู่หลังกฎ ทำให้ลืมกฎ); ref เป็นแถวยาวยังทำให้ช่วงกว้างทั้งเรื่อง. หลังย้ายกฎไปท้าย: JSON ครบทุกครั้ง แต่ยาวเกินเป้า 1.3–1.6 เท่าเมื่อบอก "ประมาณ" ตัวอักษรต่อประโยค; บอก "ไม่เกิน n" ได้ราว 0.77 n (838, 705, 631 จาก 918) จึงให้ที่ 1.2 เท่า: ครั้งแรกได้ 974 และ 887 (ครั้งหลังขาด `}` ท้าย) ราว 5.5 นาที. **temperature ร่างบท 0.7 → 0.3:** ครั้งแรกด้วย prompt เดียวกัน ค่าละ 3 ครั้ง (เป้า 918): 0.7 ผ่าน ~2/3 ยาว −31% ถึง +40%; 0.5 ผ่าน 2/3 (−1, +25, +42%); 0.3 ผ่าน 3/3 (−3, −19, −19%) ไม่วน และเล่าต่างกันทุกครั้ง; 0.1 ผ่าน 2/3 อีกครั้งเล่ายาว 46 ประโยคซ้ำครึ่งหนึ่งจนถูกตัด. ลองให้ที่ 1.35 เท่าที่ 0.3: −9, −14% แต่ครั้งหนึ่งเล่า 40 ประโยคแล้ววน จึงคง 1.2. รวมที่ 0.3 ครั้งแรกผ่าน 5 จาก 6; ครั้งที่วนนับเป็นไม่ผ่านแล้วสั่งใหม่ตามข้อ 3.

**From:** build ticket 03 · **Status:** active

## D62: ทางเลือกเล็กตอน build เสียงต่อประโยคและ render

**Chosen:** รายละเอียดที่ build ticket 04 ตัดสินเองจาก spec, conventions, Figma และโค้ดเดิม.

**Details:**
- **Kanit:** `backend.fonts` (ผู้ใช้สามที่: setup, Status check, Render job) โหลดด้วย `urllib` ใน setup เท่านั้น ตรวจ sha256 ก่อนเขียนไฟล์ marker `models/.setup/font_kanit` เป็น JSON `{files: {ชื่อ: sha256}}` เขียนท้ายสุด; แถว `font_kanit` "Kanit font" ต่อจาก `pythainlp` เทียบ marker กับค่าที่ pin และเช็คว่าไฟล์อยู่ (ไม่ hash ใหม่ทุกครั้ง); setup โหลดหลังโมเดล ก่อน `npm install`, ข้ามเมื่อแถว `ok`
- **Voice job `sentences`:** ลำดับ `busy` → ไม่มี draft หรือ id ไม่อยู่ใน draft, ซ้ำ, ไม่ใช่ list → `400` `invalid_request` → Saved voice ของ draft หาย `400` `voice_not_found` → gate → `gpu_busy`; จองช่องเป็น `voice` พร้อมคลิปของ draft (`clip_busy`) และ `draft=True` (`draft_locked`); ข้อความ `tts.Speak`/`Spoken` ส่ง clone prompt เป็น bytes ทุกประโยค; wav เขียนผ่าน `.tmp` แล้ว rename, `duration_s` ปัดถึงมิลลิวินาที; `voices.SentenceVoicer` เป็นฐานร่วมของ Voice job และ Render job; `GET /draft/sentences/{sid}/audio.wav` ไม่มีเสียง `404`
- **ค่าที่จำไว้:** `PATCH /settings` ฟิลด์อื่นนอก `watermarks` `original_volume` → `400` `invalid_settings`; ข้อความลายน้ำรวมเป็นบรรทัดเดียว 1–40 ตัวอักษรที่กินที่; `thai.width` `thai.cut_width` ย้ายจาก `script` มา `thai` (ผู้ใช้ที่สาม); `.srt` ของ Transcript และของ render เขียนด้วย `backend.clock.srt` ตัวเดียว
- **Render job:** ลำดับ `no_draft` → `missing_shots` → `disk_full` (ที่ว่างของ folder project) → `not_ready` → `busy` → `gpu_busy`; จองช่องเป็น `render` เฉพาะเมื่อมีประโยคขาดเสียง, อ่าน draft ที่จะ render ใต้ lock แล้วจึงคืนช่อง; ไฟล์กลาง `.render/{i}.mkv` (x264 `crf 12` `veryfast` + PCM) ต่อกันด้วย concat demuxer; จุดตัดของ Shot ปัดเป็นเฟรม 30 fps ของ timeline ทั้งคลิปจึงไม่เลื่อนสะสม; Shot ที่เริ่มหลังท้ายคลิป − 0.5 วินาทีเริ่มที่จุดนั้นแล้วค้างเฟรม; คลิปไม่มีเสียงหรือ `original_volume` 0 ใช้ `anullsrc`; เสียงบรรยายต่อกันด้วย `wave` ของ Python (OmniVoice ให้ rate เดียวกัน); `percent` 0–50 ตอนตัดชิ้น 50–100 ตอน encode; ชื่อซ้ำในวินาทีเดียวเลื่อนไปวินาทีถัดไป; ffmpeg รันใน `.render/` และอ้างไฟล์ด้วยชื่อเปล่า (ไม่ต้อง escape path ใน filter); `spoil_maker.ffmpeg` รวมตัวหา ffmpeg, kill เมื่อยกเลิก, อ่าน `ffmpeg -i` (ผู้ใช้ที่สอง: `frames`, `compose`)
- **ข้อความบนวิดีโอ:** ASS หนึ่ง style ต่อชนิด (`Hook`, `Title`, `Sub`, `Mark`) ตำแหน่งด้วย `\an`+`\pos` ต่อบรรทัด; ลายน้ำทึบ 80% = alpha `&H33`; ซับ A อาจเป็นคำเดียวเมื่อคำถัดไปทำให้เกิน 15 ตัวอักษร (2–4 คำเมื่อทำได้); test ไฟล์ ASS เรียก `captions.ass_file` ตรง เพราะ `.render/` ถูกลบเมื่องานจบ; อ่าน draft, ทำ timeline และต่อเสียงบรรยายใต้ lock ของ draft ก่อนคืนช่อง GPU จึงไม่มีงานเสียงใดแทรกระหว่าง `rendering`; `thai.words` เก็บช่องว่างท้ายคำ ข้อความอังกฤษจึงไม่ติดกัน; `.srt` เวลาถึงมิลลิวินาที
- **หน้าเว็บ — ตรวจแก้:** `ReviewFooter` (sticky) และ `VideoSettings` ตาม Figma; slider เสียงต้นฉบับบันทึกเองแบบช่องข้อความ (800 ms หรือปล่อย) ผ่าน `PATCH /draft`; เพิ่มลายน้ำใส่ "ลายน้ำ" ล่างขวา เล็ก แล้วเลือกข้อความไว้ให้พิมพ์ทับ (API ไม่รับข้อความว่าง); ระหว่าง `rendering` ช่องแก้ทุกช่องรอด้วย (Figma) แม้ API ให้แก้ได้; render `done` เปิด `#/spoil/renders` เอง; banner ใช้ `Alert` เดิม: `ffmpeg_failed` "render ไม่สำเร็จ", `crashed` `model_failed` "งานหยุดกลางทาง" พร้อมลองอีกครั้ง, `disk_full`; banner "แอปปิดไประหว่าง…" ของ Figma ไม่ได้ทำ เพราะงานหายเมื่อ restart (ADR-0010) ไม่มีทางรู้
- **หน้าเว็บ — ผล render:** ภาพเล็กคือเฟรมที่ 0.5 วินาทีของ mp4 (`<video preload="metadata">`) ไม่เก็บภาพแยก; player ใช้ controls ของ browser; จอ ≥ 1024 เล่นใน panel ข้างรายการ ต่ำกว่านั้นเล่นใต้แถว (`matchMedia`, video เดียวจึงไม่มีเสียงซ้อน); copy ทั้งบรรทัด "ต้นฉบับ: {ชื่อคลิป, …}"; `GPU_JOB_PATHS` ไม่เพิ่ม Voice job และ Render job (หน้า Saved voice จะนับงานของตัวเองหรือ render ที่ไม่ได้จอง GPU เป็นผู้ถือ GPU)

**Why:** อยู่ในขอบของ spec และ D9, D10, D20–D22, D30, D31, D36, D40–D42, D45, D49, D51 ไม่เปลี่ยนสิ่งที่ spec สัญญา; ทำตามรูปแบบงานลูกเดิม (thread + process ลูก + queue), conventions, docs/library-notes/ffmpeg.md และ Figma Script review, Render results.
