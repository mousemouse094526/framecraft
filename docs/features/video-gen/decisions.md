# Decisions: video-gen

ทุกข้อที่มาจาก `interview` ในไฟล์นี้ตัดสินตอน auto mode เปิด: แอปเลือกตัวเลือก (Recommended) ให้และแจ้งเจ้าของทาง Telegram; Why คือเหตุผลที่เขียนไว้ในตัวเลือกนั้น.

## D1: tab ใหม่ทำคลิปสอนกลองอย่างเดียว

**Chosen:** feature `video-gen` ทำคลิปสอนกลองแนวตั้งแบบคลิปอ้างอิง (เพจ Your Turn) อย่างเดียว: ชุดกลอง เลนโน้ต ตัวนับจังหวะ ท่อนสอน; เครื่องดนตรีอื่นเป็น feature ใหม่ทีหลัง.

**Why:** ทำแบบเดียวให้ดีก่อน; ไดอะแกรมต่อเครื่องดนตรีเป็นงานใหญ่คนละชิ้น.

**Rejected:**
- สอนดนตรีหลายเครื่องตั้งแต่แรก — งานใหญ่ขึ้นหลายเท่า ต้องมีไดอะแกรมต่อเครื่อง
- แม่แบบวิดีโอเป็นชั้นทั่วไปไม่ผูกดนตรี — ไม่มีอะไรให้ซิงก์กับเสียงถ้าไม่มีโน้ต

**From:** interview · **Status:** active

## D2: โน้ตกรอกในแอป แล้วสร้างเสียงกลองจาก sample

**Chosen:** ผู้ใช้กรอกโน้ตบนตาราง (ชิ้นกลอง × ช่อง) และ BPM; แอปผสมเสียงกลองจาก sample ที่มากับ project. รายการโน้ตชุดเดียวขับทั้งเสียงและภาพ.

**Why:** เสียงกับภาพตรงกันเป๊ะเพราะมาจากโน้ตชุดเดียว ไม่ต้องใช้ AI.

**Rejected:**
- นำเข้าไฟล์ MIDI — ต้องมีไฟล์ MIDI ก่อนทุกครั้ง
- อัปเสียงกลองจริงแล้วให้ AI ถอดโน้ต — โมเดล drum transcription ในเครื่องแม่นยำต่ำ งานใหญ่มาก

**From:** interview · **Status:** active

## D3: Pillow วาดกราฟิกทีละเฟรม ส่งเข้า ffmpeg; ตัวหนังสือให้ libass วาด

**Chosen:** Python วาดกราฟิกทุกเฟรม (พื้นหลัง ชุดกลอง ไม้กลอง เลนโน้ต playhead วง L/R) ด้วย Pillow แล้วส่ง RGB ดิบเข้า ffmpeg ทาง stdin; ตัวหนังสือทุกชิ้นเป็นไฟล์ ASS ที่ filter `ass` วาดทับ แบบ render เดิม.

**Why:** ทุกเฟรมคำนวณจากเวลา t ตรงๆ เทสทีละเฟรมได้; Pillow มีใน venv แล้ว.

**Rejected:**
- ffmpeg filter กับ ASS ล้วน (`\p`, `\move`, `\t`) — ไม้กลองหมุนและเลนโน้ตเขียนเป็น ASS ยากและเทสยาก
- browser headless อัดจอ (แบบ Remotion) — ต้องเพิ่ม browser เข้า Setup script หนักและช้า

**Details:**
- วาดที่ 2 เท่า (2160×3840) แล้วย่อด้วย lanczos ให้ขอบเนียน เพราะ `ImageDraw` ไม่ทำ anti-alias ให้รูปทรง
- ตัวหนังสือไม่วาดด้วย Pillow เพราะภาษาไทยต้อง shaping ที่ libass ทำผ่าน harfbuzz อยู่แล้ว (`docs/library-notes/ffmpeg.md`)
- Pillow ยังไม่ pin (มากับ diffusers) — build ใส่เป็น dependency ตรงใน `pyproject.toml` pin ตาม `uv.lock`

**From:** interview · **Status:** changed by D18

## D4: จังหวะหลักเดียว เล่นซ้ำในหลายท่อนสอน

**Chosen:** บทเรียนกลองหนึ่งอันมี Groove 1–4 ห้องชุดเดียว และท่อนสอน 1–6 ท่อนเรียงกัน; แต่ละท่อนเล่น Groove ซ้ำตามจำนวนรอบ มีป้าย คำอธิบาย ชิ้นที่เน้น และความเร็วของตัวเอง.

**Why:** ตรงคลิปอ้างอิง (KICK → FLAMS → YOUR TURN. เล่นจังหวะเดียวกันโดยเน้นคนละชิ้น) และกรอกโน้ตครั้งเดียว.

**Rejected:**
- แต่ละท่อนมีจังหวะของตัวเอง — ยืดหยุ่นกว่า แต่กรอกโน้ตหลายรอบ
- จังหวะเดียวไม่มีท่อน — ไม่ได้สไตล์สอนทีละส่วน

**Details:**
- ช่องของท่อนสอนอยู่ใน spec › Data

**From:** interview · **Status:** active

## D5: 4/4 ช่องละโน้ตเขบ็ต 2 ชั้น (16 ช่องต่อห้อง)

**Chosen:** อัตราจังหวะ 4/4 อย่างเดียว ห้องละ 16 ช่อง; โน้ตแต่ละตัวมีชิ้นกลอง ช่อง ไม้ (R, L หรือไม่มี) และลักษณะตี (ปกติ, เน้น, เบา, flam).

**Why:** ครอบคลุมคลิปอ้างอิง (1e&a) และ groove ร็อก/ป๊อปส่วนใหญ่; flam เป็นลักษณะตีของโน้ต ไม่ใช่ช่องเพิ่ม.

**Rejected:**
- เลือกอัตราได้ (3/4, 6/8) และสามพยางค์ — editor และเลนโน้ตซับซ้อนขึ้นมาก

**From:** interview · **Status:** active

## D6: พื้นหลังสีเข้มที่แอปวาด หรือภาพของผู้ใช้

**Chosen:** ตั้งต้นพื้นกรมท่าไล่สีเข้มที่แอปวาดเอง; เลือกไฟล์ PNG หรือ JPG ในเครื่องเป็นพื้นหลังได้ แอปครอป 9:16 เบลอ และทำมืดให้อ่านง่าย.

**Why:** คลิปอ้างอิงใช้ปกอัลบั้มที่มีเจ้าของลิขสิทธิ์; ตั้งต้นจึงไม่มีภาพ ส่วนภาพที่ผู้ใช้เลือกเป็นเรื่องสิทธิ์ของผู้ใช้.

**Rejected:**
- สีเข้มอย่างเดียว — ทุกคลิปหน้าตาเหมือนกัน
- ภาพ AI จาก klein — จอง GPU และช้า ไม่คุ้มกับพื้นที่เบลอมืดอยู่แล้ว

**From:** interview · **Status:** active

## D7: เสียงกลองล้วน ไม่ใช้คลังเสียงพื้นของ toon

**Chosen:** เสียงของคลิปเป็นกลองที่แอปผสมอย่างเดียว ไม่มี backing track; ไม่ใช้คลังเสียงพื้น (toon D16).

**Why:** ตรงคลิปอ้างอิง (กลองเดี่ยว); เพลงในคลังไม่มี tempo และจุดเริ่มห้อง จะไม่ตรงกับกลอง และเพลงต้นฉบับมีลิขสิทธิ์.

**Rejected:**
- เลือกเสียงจากคลังแล้วตั้ง offset เอง — ผู้ใช้ต้องตั้ง BPM ให้ตรงเพลงเอง

**Details:**
- ของเดิมที่ใช้ซ้ำแทน: ตัวจัดการผล render (`backend.renders`), ffmpeg runner (`backend.ffmpeg`), ตัวเขียน ASS (`backend.subtitles`), ตัวรับไฟล์ดิบ (`backend.uploads`), `JobSlot` (`backend.jobs`)

**From:** interview · **Status:** active

## D8: ปุ่ม "ฟังจังหวะ" สร้างเสียงอย่างเดียวก่อน render

**Chosen:** backend ผสมเสียงกลองของบทเรียนทั้งคลิปด้วยตัวผสมเดียวกับ render แล้วหน้าเว็บเล่นให้ฟัง; ภาพดูจากผล render จริงเท่านั้น (แบบ toon D18).

**Why:** ฟังว่ากรอกโน้ตถูกได้ในไม่กี่วินาที โดยไม่ต้องเขียนตัววาดชุดที่สองในเบราว์เซอร์.

**Rejected:**
- ไม่มีตัวอย่าง render แล้วดู — กรอกผิดต้อง render ใหม่ทั้งคลิป
- ตัวอย่างภาพและเสียงสดในเบราว์เซอร์ (canvas, WebAudio) — ต้องเขียนตัววาดสองชุดที่ต้องตรงกัน

**From:** interview · **Status:** active

## D11: sample กลองจาก Big Rusty Drums (CC0) โหลดผ่าน Setup script

**Chosen:** ใช้ sample ไมค์ใกล้ (`cl`) ของ Karoryfer Big Rusty Drums (CC0 1.0) จาก repo `sfzinstruments/karoryfer.big-rusty-drums` pin commit `f07ce00`; Setup script โหลดเฉพาะไฟล์ที่ใช้ทีละไฟล์พร้อม sha256 ลง `models/drums/`; Status check มีแถว `drum_kit`.

**Why:** ชุดเดียวที่เป็น CC0 (ไม่ต้องให้เครดิต) และมีครบ 10 ชิ้นรวมทอม 3 ใบ มีหลายระดับความแรงพอทำโน้ตเบาและ flam ขนาดราว 31 MB.

**Rejected:**
- Versilian Virtuosity Drums (CC0) — ไม่มีทอมกลาง เสียงแจ๊ส 264 MB
- DrumGizmo DRSKit (CC-BY 4.0) — ต้องให้เครดิตทุกคลิป ต้องผสม 13 ไมค์เอง
- ชุดที่เป็น GPL — เงื่อนไขกับเสียงที่ render ออกไม่ชัด

**Details:**
- ไฟล์เป็น git blob ธรรมดา (ไม่ใช่ LFS) โหลดผ่าน `raw.githubusercontent.com/{owner}/{repo}/{commit}/{path}` ได้ทีละไฟล์ แบบ font Kanit (spoil-maker D21)
- ตำแหน่ง `models/drums/` ตาม ADR-0003; pin และ sha256 ตาม ADR-0004; แถวเดียวที่ Status check ตาม ADR-0009
- ชิ้นกลองกับ folder ของ sample อยู่ใน spec › Implementation › Drum kit

**Sources:** [Big Rusty Drums LICENSE](https://github.com/sfzinstruments/karoryfer.big-rusty-drums/blob/f07ce00df34a46b6b08375be56fe116cf15782bc/LICENSE)

## D13: ทางเลือกเล็กของภาพและเสียงที่ตัดสินจากคลิปอ้างอิง

**Chosen:** ชุดข้อตัดสินเล็กที่อ่านจากเฟรมของคลิปอ้างอิงและความยาวของมัน.

**Details:**
- **เลนโน้ต:** 3 เลน (ฉาบบน, สแนร์กับทอมกลาง, กระเดื่องกับไฮแฮทเท้าล่าง) ไม่ใช่บรรทัดห้าเส้น; playhead อยู่กับที่ โน้ตเลื่อนผ่าน — ตามเฟรมจริง
- **นับเข้า:** ก่อนท่อนแรกมีนับเข้า 1 ห้องด้วยเสียงไฮแฮทปิดเบา ตัวนับขึ้น 1–4 — คลิปอ้างอิงเริ่มด้วยตัวนับก่อนเข้าจังหวะ
- **ตัวนับจังหวะ:** แสดงเลขจังหวะ 1–4 ของห้องที่กำลังเล่น เปลี่ยนตรงต้นจังหวะ — ตามเฟรมจริง
- **ไม้กลอง:** ไม้มือที่ตีขยับจากจุดพักไปชิ้นกลองใน 0.12 วินาทีก่อนโน้ต วงแหวนแดงที่ชิ้นที่ถูกตีจาง 0.15 วินาที; ป้ายเท้า RF และ LF เต้นเมื่อเท้าตี — ตามเฟรมจริง
- **ชิ้นที่ไม่เน้น:** ความสว่าง 35% ในท่อนที่เลือกชิ้นที่เน้นไว้; ไม่เลือก = ทุกชิ้นสว่าง — ตามเฟรม KICK
- **ความยาว:** คลิปทั้งหมด (นับเข้า + ทุกท่อน) ไม่เกิน 90 วินาที — คลิปอ้างอิงยาว 19 วินาที รูปแบบ reels
- **ไฟล์ผล:** mp4 1080×1920 30 fps กับ `.srt` ของป้ายและคำบรรยาย ตามที่ `backend.renders` เก็บ
- **ความแรง:** เน้น = ชั้นแรงสุดของ sample, ปกติ = ชั้นกลาง, เบาและโน้ตนำของ flam = ชั้นเบาสุด; round-robin วนตามลำดับเพื่อให้ render ซ้ำได้ไฟล์เดิม

**From:** code · **Status:** changed by D21

## D14: Render job ทีละงาน ไม่จองช่อง GPU

**Chosen:** Render job ของ tab สอนกลองมี `JobSlot` ของตัวเอง ทีละงาน แสดง % ยกเลิกได้ ไม่จองช่อง GPU เพราะไม่มีโมเดล; render ระหว่างงาน GPU ของ tab อื่นได้.

**Why:** ไม่มีงาน AI ในทางนี้ (D2); แบบเดียวกับ Render job ของการ์ตูนเล่าที่มี slot ของตัวเอง (toon D45).

**Rejected:**
- คิว render หลายงาน — ทีละงานพอสำหรับผู้ใช้คนเดียว (ADR-0010)

**Details:**
- encoder ตาม spoil D36: Mac `h264_videotoolbox`, Windows `libx264`, เสียง `aac`
- เป้าความเร็ว: คลิป 30 วินาที render จบใน ≤ 60 วินาทีบน Mac Apple Silicon (≤ 2 เท่าความยาวคลิป)
- เป้าความตรง: เสียงโน้ตเริ่มในเฟรมเดียวกับที่ภาพแสดงการตี (คลาดไม่เกิน 1 เฟรม 33 ms)

**From:** code · **Status:** active

## D15: seam ของ video-gen

**Chosen:** สาม seam: API ด้วย ffmpeg จริง, ฟังก์ชันวาดเฟรมจากเวลา (`frame_at`) กับตารางเวลาโน้ต, และหน้าเว็บผ่าน `App` กับ fetch ปลอม.

**Why:** ทางนี้ไม่มีโมเดล จึงทดสอบด้วยของจริงได้ทั้งทาง; ตารางเวลาโน้ตเป็นที่เดียวที่ความตรงของเสียงกับภาพตัดสิน.

**Rejected:**
- เทสเฉพาะผ่าน API — ดูไม่ได้ว่าภาพเฟรมหนึ่งแสดงการตีตรงเวลาหรือไม่

**Details:**
- แบบเดียวกับ toon D42 และ story-kb D18

**From:** code · **Status:** active

## D16: บันทึกบทเรียนที่ยาวเกินได้ กันที่ฟังและ render

**Chosen:** `PUT` บันทึกบทเรียนที่ยาวเกิน 90 วินาทีได้; `too_long` ตอบเฉพาะ `POST /listen` และ `POST /render`; หน้าแก้แสดงว่าเกินกี่วินาที.

**Why:** red team (The Advocate): กันที่ `PUT` ทำให้ผู้ใช้ที่เพิ่มท่อนเกินเพดานบันทึกไม่ได้และเสียงานเมื่อออกจากหน้า.

**Rejected:**
- กันที่ `PUT` — เพิ่มท่อนเกินแล้วบันทึกไม่ได้ ต้องตัดทันที

**From:** red team · **Status:** active

## D17: ชุดกลองวาดด้วยโค้ดตามตำแหน่งใน kit-sketch

**Chosen:** `kit` วาดชุดกลองด้วยรูปทรง Pillow ตามตำแหน่ง ขนาด จุดกระทบ และจุดพักไม้ใน [kit-sketch.md](kit-sketch.md) ที่วัดจากคลิปอ้างอิง; ไฮแฮทวาดชิ้นเดียวใช้ร่วมสาม `piece`.

## D23: ข้อแก้จาก legal

**Chosen:** ทำตามเงื่อนไข CONDITIONAL ของ legal ข้อ 2–4 ในตัวแอป.

**Details:**
- **ป้ายตั้งต้น:** ท่อนที่สองของบทเรียนใหม่ใช้ป้าย `ลองเล่นเอง` ไม่ใช่ `YOUR TURN.` — legal ข้อ 4 ยังไม่รู้ว่า "Your Turn" จดเครื่องหมายการค้าในไทยหรือไม่

- **ก่อนหารายได้:** ตรวจ legal ข้อ 2 ใหม่ (s.32(6) ครอบเฉพาะไม่หากำไร) — เป็นเรื่องของการเผยแพร่ ไม่ใช่ของแอป

## D36: ภาพพื้นหลังส่งแบบ ADR-0028: `check` ก่อน แล้ว `PUT ?size=`

**Chosen:** หน้าเว็บส่ง `POST /lessons/{id}/background/check` `{size}` ก่อน (`413` `file_too_large`, `409` `lesson_busy`, `404`, `507` `disk_full`) แล้ว `PUT /lessons/{id}/background?size={bytes}` body ดิบ; backend รับด้วย `uploads.receive` ตัวเดียวกับ spoil และ toon. `PUT` เช็คซ้ำทุกข้อ และเพิ่ม `400` `size_mismatch`, `415` `unsupported_image`. route นี้เข้ารายการข้อยกเว้นของ ADR-0028.

**Why:** ADR-0028 ให้หน้าเว็บส่ง JSON `check` ก่อน เพราะ server ที่ตอบ error ก่อนรับ body ครบทำให้ browser เห็นแค่ network error; ตาราง API ของ spec มีแค่ `PUT`. ถามเจ้าของแล้ว auto mode เลือกตัวเลือก (Recommended): ทำตาม ADR และแก้ spec › API.

**Rejected:**
- `PUT` route เดียวตาม spec เดิม อ่าน body จนหมดก่อนตอบ error — ต้องเขียนข้อยกเว้นของ ADR-0028 สำหรับ route นี้

**From:** build ticket 03 · **Status:** active

## D37: ทางเลือกเล็กของภาพพื้นหลัง

**Chosen:**
- `GET /lessons/{id}/background.jpg` ให้หน้าแก้แสดงภาพ; หน้าเว็บขอด้วย `?v={updated_at}` ภาพใหม่จึงเป็น URL ใหม่ (`404` เมื่อไม่มีภาพ)
- `PUT` และ `DELETE` ภาพตอบ `200` พร้อมบทเรียน และตั้ง `updated_at` ใหม่; `DELETE` ตอนไม่มีภาพก็ `200`
- `file_too_large` ตอบ `413` ตาม spec (`uploads.require_size` รับ status; toon ยัง `400`)
- body ที่รับเขียนเป็น `.tmp` ใน `media/drums/.partial/`; jpg ที่ครอปแล้วเขียนข้างกันแล้ว rename เป็น `background.jpg` ใต้ `lessons.lock`: start-up ลบ `.tmp` ที่ค้าง (`files.remove_unfinished`), บทเรียนที่ถูกลบระหว่างรับเป็น `404`
- JPEG quality 92: ภาพถูกเบลอและทับดำทุก render
- หน้าแก้ไม่มีแถบ %: ไฟล์ ≤ 20 MB ในเครื่องเดียวกัน ปุ่มเป็น "กำลังส่งภาพ…" และกดไม่ได้จนตอบ
- ภาพที่ได้รับเปลี่ยนเฉพาะ `background` ของฟอร์ม สิ่งที่พิมพ์ค้างไว้ยังไม่บันทึกและอยู่ต่อ; error ข้างปุ่ม ไม่ใช่ใต้ฟอร์ม
- แสดงภาพเป็นกรอบ 9:16 ข้างปุ่ม ไม่มีภาพ = กรอบสีของแอปพร้อมคำ "สีของแอป"

**Why:** ข้อเลือกภายใน feature ที่ไม่เปลี่ยนสิ่งที่ spec สัญญา; หน้าตาใช้ของเดิมของแอปจนกว่าแถว design ของหน้าแก้จะปิด (D29).
